Estate Rental Platform

A Flask and Oracle rental application where the business rules are enforced by the database rather than by the web layer.

Tenants browse listings, check availability and request reservations; owners publish properties and confirm or reject requests. The design question behind the project was where each rule should live — and the answer, for anything that must never be bypassed, was Oracle.

Design principle

A rental platform has rules that must hold regardless of how a record is created: two confirmed reservations cannot overlap on the same property, a tenant cannot book on someone else's behalf, a successful payment cannot be edited afterwards.

Implementing those checks in Flask would place them one layer above the data. Any other client — a script, a direct SQL session, a future mobile backend — would bypass them entirely. So the rules that matter are implemented as Oracle triggers and stored procedures, and Flask handles routing, sessions and presentation.

LayerResponsibility
FlaskRoutes, sessions, role-based navigation, error handling, templates
PL/SQLBusiness operations, integrity rules, identity enforcement
Oracle modelTables, constraints, indexes, views, roles and grants

The trade-off is real and worth stating: logic in the database is harder to version, test and debug than application code, and it ties the project to Oracle. The reason to accept that here is enforcement — a trigger cannot be skipped.

The separation between RESERVATION and LOCATION is deliberate: a reservation is a request that may be refused, a location is a confirmed contract. Confirmation creates the second from the first, so a rejected request leaves no contractual trace.

Business logic

Nineteen stored procedures and functions implement the operations. The booking lifecycle runs through them end to end.

Booking lifecycle

  1. verifierDisponibilite() — counts conflicting reservations for a property and date range
  2. creerReservation() — creates the request, or raises -20001 if the period is taken
  3. confirmerReservation() — validates dates, computes the total and creates the LOCATION row
  4. calculerPrixTotal() — nights multiplied by nightly rate
  5. genererPaiement() → validerPaiement() / echouerPaiement()
  6. emettreRemboursement() — refund path
  7. majNoteMoyenne() — recomputes the property rating after a review

Availability check

Overlap detection is the core rule. The procedure calls the availability function first, and aborts the whole transaction if a conflict exists. 

CREATE OR REPLACE PROCEDURE creerReservation(
    p_id_locataire NUMBER,
    p_id_bien      NUMBER,
    p_date_deb     DATE,
    p_date_fin     DATE
) IS
    v_conf   NUMBER;
    v_id_res NUMBER;
BEGIN
    v_conf := verifierDisponibilite(p_id_bien, p_date_deb, p_date_fin);

    IF v_conf > 0 THEN
        RAISE_APPLICATION_ERROR(-20001, 'Bien non disponible sur ces dates');
    END IF;

    INSERT INTO RESERVATION(id_locataire, id_bien, id_annonce,
                            date_demande, date_debut, date_fin, statut)
    VALUES(p_id_locataire, p_id_bien, NULL,
           SYSDATE, p_date_deb, p_date_fin, 'EN_ATTENTE')
    RETURNING id_reservation INTO v_id_res;

    COMMIT;
EXCEPTION
    WHEN OTHERS THEN ROLLBACK; RAISE;
END;

Search results stay consistent with this rule: rechercherBiens() excludes conflicting properties through a NOT EXISTS subquery, so a property that cannot be booked never appears as available in the first place.

Integrity rules

Each of these triggers exists because of a specific way the data could be corrupted. They are listed with the error code they raise, since that is what the Flask layer catches and translates for the user.

RuleMechanismError
A property with active reservations cannot be deleted trg_no_delete_bien_with_active_res -20010
A successful payment cannot be modified trg_no_update_paiement_if_reussi -20011

Payment immutability

Once statut_paiement = 'REUSSI', the row is frozen. Correcting a payment therefore requires an explicit refund through emettreRemboursement(), which leaves a trace, rather than an update that would erase the original state. This is the rule that most clearly belongs in the database rather than in application code.

Rating updates

majNoteMoyenne() is declared AUTONOMOUS_TRANSACTION, so recomputing the average commits independently of the transaction that inserted the review. Without it, the procedure would be modifying a table already involved in the firing statement.

Security model

Identity enforcement

The most direct attack on a platform like this is acting as someone else — booking under another tenant's identity, or sending a message with a forged sender. Two triggers close that path by overwriting the submitted identifier with the identity of the connected database user. 

CREATE OR REPLACE TRIGGER trg_secu_resa_locataire
BEFORE INSERT ON RESERVATION
FOR EACH ROW
DECLARE
    v_user_id NUMBER;
BEGIN
    IF USER IN ('AIRBNB_V2', 'SYSTEM', 'SYS') THEN RETURN; END IF;

    SELECT id_utilisateur INTO v_user_id
    FROM UTILISATEUR WHERE login_db = USER;

    IF :NEW.id_locataire != v_user_id THEN
         :NEW.id_locataire := v_user_id;
    END IF;
END;

Each application user maps to an Oracle account, so USER is a trustworthy identity — not a value the client can set. The same pattern protects messaging through trg_secu_message_identity.

Ownership enforcement

Four triggers verify that the connected owner actually owns the object being modified, following the foreign key back to BIEN where needed:

  • trg_secu_bien_owner — properties
  • trg_secu_annonce_owner — listings, checked through the linked property
  • trg_secu_photo_owner — photos
  • trg_secu_equipement_owner — amenities

Outcome

The full cycle works end to end: publish, search, reserve, confirm, pay, review. Thirty-nine PL/SQL objects — nineteen procedures and functions, ten triggers, ten views — carry the rules, backed by five database roles.

What the project taught me, and what I would defend:

  • Enforcement belongs where it cannot be bypassed. Identity triggers that overwrite the submitted value are stronger than a validation check in a route handler, because they hold for every client.
  • Immutability beats correction. Freezing successful payments and requiring an explicit refund keeps a history that an update would destroy.
  • Views are an access-control tool, not only a convenience — granting a role a view instead of a table decides what it can read at the schema level.

Known weaknesses

Two of these I would fix before deploying this anywhere real:

  • Password hashing uses MD5 without a salt. sInscrire() and seConnecter() hash through DBMS_CRYPTO.HASH_MD5. MD5 is broken for password storage and an unsalted digest is vulnerable to rainbow tables; a slow salted algorithm is what this should use.
  • The availability check is not concurrency-safe. verifierDisponibilite() counts conflicts and creerReservation() then inserts. Two concurrent transactions can both pass the check before either commits, and both bookings are written. Closing this requires locking the property row or enforcing non-overlap as a constraint rather than a procedural check.
  • Identity correction is silent. trg_secu_resa_locataire rewrites a mismatched tenant identifier rather than raising. It prevents the attack, but leaves no signal that one was attempted; raising an error would also make the rule visible during debugging.
  • No automated tests. The procedures are exercised manually. Edge cases around dates, status transitions and concurrency deserve a test suite.

Next steps

  • Replace MD5 with a salted, slow hash and migrate stored credentials.
  • Make booking concurrency-safe through row locking or an exclusion constraint.
  • Add an audit table for payment and status changes.
  • Build a PL/SQL test suite covering the eight integrity rules.
