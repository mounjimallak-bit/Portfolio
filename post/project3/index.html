Bien Immobilier — Plateforme de Location

Flask Oracle PL/SQL Tailwind

Application web de location immobilière couvrant le cycle complet : publication, recherche, réservation, validation, paiement et avis. L’objectif était de construire une solution robuste orientée transaction, avec une logique métier centralisée en PL/SQL (anti-overbooking, statuts, paiements, intégrité) et une interface claire côté Flask.

Pourquoi ce projet intéresse un recruteur ?
Parce qu’il prouve que tu sais construire un backend “propre” : auth + rôles, workflow métier, intégrité DB, gestion des erreurs et séparation des responsabilités (UI / Flask / PL/SQL / Oracle).

Vue d’ensemble

Bien Immobilier est conçu comme une application data-driven : l’interface consomme des vues Oracle (biens publics, note moyenne, photo principale) et les règles critiques sont garanties côté base via PL/SQL. Cela permet de garder une cohérence solide même si l’interface évolue.

Architecture en couches

  • Présentation : HTML/CSS/Tailwind (UI)
  • Applicatif : Flask (auth, sessions, RBAC, endpoints)
  • Logique métier : PL/SQL (procédures / fonctions / triggers)
  • Données : Oracle (modèle relationnel, contraintes, vues)

Qualité & fiabilité

  • Validation des entrées (dates, montants, champs obligatoires)
  • Gestion des erreurs (messages utilisateurs + rollback transaction)
  • Sécurité : sessions, contrôle d’accès, protections côté DB

Fonctionnalités

Locataire

  • Parcourir & rechercher des logements
  • Voir détail + périodes indisponibles
  • Envoyer une demande de réservation
  • Paiement (workflow) + avis après séjour

Propriétaire

  • Publier / modifier / supprimer des biens
  • Gérer les demandes (accepter/refuser)
  • Suivre l’état des réservations

Bonus : affichage des notes, photo principale, agrégations via vues SQL, et statuts de réservation pour un suivi clair.

Modélisation & Couche Données (Oracle)

Modèle relationnel normalisé couvrant utilisateurs, biens, réservations, locations, paiements et avis. Le système s’appuie sur des contraintes d’intégrité + triggers pour sécuriser les opérations critiques.

Entités clés

  • UTILISATEUR → (LOCATAIRE / PROPRIETAIRE)
  • BIEN, PHOTO_BIEN, AVIS_BIEN
  • RESERVATION → LOCATION → PAIEMENT

Vues / requêtes

  • VUE_BIENS_PUBLICS : photo principale + note moyenne + infos
  • Vues dashboard : réservations par statut, revenus/activité, historique

Défis techniques, bugs rencontrés & solutions

Ici je liste volontairement des problèmes “réels” (et pas juste des features) : c’est exactement ce qui prouve ta maturité technique.

1) Anti-overbooking (chevauchement de dates)

Bug : deux réservations pouvaient être acceptées si elles arrivaient très proches (concurrence).
Solution : contrôle côté DB : vérification de chevauchement en PL/SQL + transaction atomique. Rejet immédiat si une période existe déjà (même si l’app Flask a un bug).

2) Incohérence de statuts (réservation/paiement)

Bug : paiement “validé” alors que réservation “refusée” (workflow mal verrouillé).
Solution : machine à états : statuts autorisés (PENDING → ACCEPTED → PAID → REVIEWED). Triggers/contrôles PL/SQL pour empêcher toute transition interdite.

3) Sécurité : accès à des données d’un autre propriétaire

Bug : un utilisateur pouvait tenter d’accéder à un bien via un ID dans l’URL.
Solution : double protection : contrôle RBAC côté Flask (session + owner_id) + requêtes SQL filtrées par propriétaire pour empêcher l’usurpation.

4) Paiement non modifiable (immutabilité)

Bug : UPDATE possible sur paiement après validation (risque de fraude / incohérence).
Solution : trigger de protection : un paiement validé devient “read-only”. Toute tentative de modification est bloquée côté base.

5) Performance sur la page d’accueil (liste des biens)

Bug : page lente à cause d’agrégations répétées (notes + photos).
Solution : création de vues SQL (photo principale + moyenne des avis) pour éviter des requêtes multiples depuis Flask et garder un affichage rapide.

6) Gestion des erreurs / rollback

Bug : en cas d’erreur DB, l’app pouvait laisser une réservation “partiellement créée”.
Solution : transactions + rollback et messages UI propres (retour utilisateur clair), avec logs côté serveur pour debug.

Choix techniques (justifiés)

Pourquoi Oracle + PL/SQL ?

  • Transactions fiables et intégrité forte
  • Logique métier garantie côté DB (procédures, triggers)
  • Vues/agrégations pour des pages rapides et stables

Pourquoi Flask ?

  • Backend léger et flexible
  • Routes claires + templates Jinja2
  • Connexion Oracle via python-oracledb
