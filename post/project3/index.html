Bien Immobilier — Plateforme de Location

Flask Oracle PL/SQL Tailwind

Application web de location immobilière permettant la gestion complète du cycle : publication, réservation, validation, paiement et avis. Le projet met l’accent sur la cohérence transactionnelle, la logique métier en PL/SQL et une base Oracle structurée.

Livrables : application Flask, scripts SQL/PLSQL, schéma BD, démo vidéo.

Stack & concepts

  • Backend : Flask (sessions, auth, routes, guards)
  • DB : Oracle SQL / PL/SQL (procédures, vues, triggers)
  • UI : HTML / CSS / Tailwind + Jinja2
  • Règles métier : statuts de réservation, anti-chevauchement, paiement, avis

Vue d’ensemble

Bien Immobilier est conçu comme une application data-driven : l’interface consomme des vues Oracle et la logique critique est centralisée dans la base via PL/SQL. L’objectif est d’obtenir une plateforme stable, cohérente et maintenable.

Architecture en couches

  • Présentation : HTML/CSS/Tailwind (UI)
  • Applicatif : Flask (auth, sessions, RBAC, endpoints)
  • Logique métier : PL/SQL (procédures / fonctions / triggers)
  • Données : Oracle (modèle relationnel, contraintes, vues)

Fonctionnalités

Locataire

  • Parcourir & rechercher des logements
  • Voir détail + périodes indisponibles
  • Envoyer une demande de réservation
  • Payer (workflow) + laisser un avis

Propriétaire

  • Publier / modifier / supprimer des biens
  • Gérer les demandes (accepter/refuser)
  • Suivre l’état des réservations

Bonus : affichage des notes, photo principale, agrégations via vues SQL.

Modélisation & Couche Données (Oracle)

Modèle relationnel normalisé couvrant utilisateurs, biens, réservations, locations, paiements et avis. La base utilise des contraintes d’intégrité, des vues et des procédures PL/SQL.

Entités clés

  • BIEN, PHOTO_BIEN, AVIS_BIEN
  • RESERVATION → LOCATION → PAIEMENT

Vues utilisées

  • VUE_BIENS_PUBLICS (photo principale, note, infos)
  • Vues/queries dashboard (propriétaire/locataire)

Défis techniques & solutions

Les règles critiques sont traitées côté Oracle pour garantir robustesse et cohérence, même si l’application évolue côté Flask.

Anti-overbooking

Empêcher le chevauchement de réservations via une vérification des dates avant insertion (SQL) et un workflow PL/SQL (ex : creerReservation).

Immuabilité du paiement

Une fois validé, un paiement ne peut pas être modifié (contrôle côté Oracle, ex : trigger de protection) afin d’éviter des manipulations post-transaction.

Contrôle d’accès propriétaire

Un propriétaire ne peut gérer que ses propres biens. Contrôle en couche Flask (RBAC) et protection côté base pour éviter l’usurpation.

Notes & agrégations

Mise à jour des métriques (note moyenne) et agrégations via PL/SQL + vues afin d’alléger les requêtes Flask et garder des informations à jour.

Choix techniques (justifiés)

Pourquoi Oracle + PL/SQL ?

  • Transactions fiables et intégrité forte
  • Centralisation de la logique métier (procédures, triggers)
  • Requêtes avancées + vues pour l’agrégation

Pourquoi Flask ?

  • Backend léger et flexible
  • Routes claires + Jinja2 pour pages dynamiques
  • Intégration simple avec Oracle via python-oracledb
