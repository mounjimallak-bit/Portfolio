Axiora Data

An analytics platform for the socio-economic indicators of the Souss-Massa region, built on open data published by Morocco's High Commission for Planning (HCP).

This page documents how the platform was built: what the raw data looked like, why it had to be cleaned before anything else, how statistical tables were joined to geographic boundaries, and what the forecasting module does and does not claim.

Open the live app View source

Context

Morocco's High Commission for Planning publishes a large volume of territorial statistics: census results, poverty and vulnerability rates, labour market indicators, housing, education, health and local finance. The data is public and detailed, but it is distributed as PDF documents and raw spreadsheets.

That format makes some questions expensive to answer. Comparing a province across three census years, or ranking communes by poverty rate, means opening several files, reconciling inconsistent labels and rebuilding the same tables by hand each time. The information exists; reaching it is the obstacle.

Axiora Data loads those files once, harmonises them, and exposes them through a single interface where an indicator can be filtered, mapped, compared across years and extrapolated. It covers six domains — population, labour, housing, finance, education and poverty — for the Souss-Massa region.

What the platform does

  • Explores indicators by year, province and commune, with year-on-year variation
  • Renders choropleth maps of poverty and vulnerability at province and commune level
  • Projects indicator trends forward using linear regression
  • Answers questions in natural language, constrained to the loaded dataset
  • Generates a formatted PDF report from any selected dataset

Architecture

The application is a single Streamlit process. Data preparation happens once, at import time, and everything downstream reads from memory.

  1. Sources — fifteen HCP spreadsheets covering six domains, organised by province and commune, spanning 2004 to 2024.
  2. Preparation — cleaning, type conversion, missing-value handling and label normalisation with pandas and NumPy.
  3. Consolidation — all cleaned datasets merged into one Python dictionary (hcpdata.py).
  4. Analysis — KPIs, year-on-year variation, top and bottom rankings computed on demand.
  5. Visualisation — interactive charts with Plotly; choropleth maps with GeoPandas.
  6. Forecasting — linear regression with a strict temporal train/test split (scikit-learn).
  7. Assistant and reporting — Gemini API for question answering, fpdf for report generation.

Holding the cleaned data in a single in-memory dictionary rather than reading files on each interaction keeps the interface responsive, and gives the assistant one consistent structure to work from.

Why cleaning came first

HCP spreadsheets are designed to be read by people, not parsed by programs. Five recurring problems made them unusable as-is:

  • Thousands separated by spaces — 421 844 is a string, not a number
  • Percentages carrying their symbol — 49,8% needs extraction before conversion
  • Comma decimal separator (French convention) — silently breaks float()
  • Partially empty hierarchical rows — subtotal lines such as "Rural" or "Centre" that are not observations
  • Column names varying between exports — the same field spelled differently across files

Left unhandled, each of these produces a plausible but wrong result rather than an error: a column read as text sorts alphabetically, a subtotal row counted as an observation inflates every average. Cleaning is what makes the rest of the platform trustworthy.

Stripping whitespace, collapsing repeated spaces and removing invisible characters, so that joins and transformations match on stable keys.

import re
import pandas as pd
import numpy as np

def to_number(x):
    if pd.isna(x):
        return np.nan
    s = str(x)
    s = s.replace(" ", "").replace("\u202f", "").replace("\xa0", "")  
    s = s.replace("%", "")                                            
    s = s.replace(",", ".")                                            
    s = re.sub(r"[^0-9\.\-]", "", s)                                
    return pd.to_numeric(s, errors="coerce")

Consolidation

After cleaning, the platform no longer depends on scattered files. Every dataset is consolidated into one nested Python dictionary in hcpdata.py, keyed by domain, then by province, then by indicator. This single structure feeds the pandas DataFrames behind each chart and supplies the assistant with one consistent, hierarchical context.

Labour market

Averages hide the structure that matters here. This module separates participation by sex and by urban or rural setting, so that gaps rather than levels become visible.

The heatmap reads the gap between male and female participation over time; the second view shows how that gap differs between urban and rural territories. Male participation remains substantially higher across the whole period, and the urban/rural split separates two different sets of constraints — access to employment, mobility, and locally available opportunities.

Housing

Spread indicates inequality between territories; isolated points usually mark rapid urbanisation or a specific development project. Both are more useful for prioritisation than the regional average.

    gdf_provinces = load_shapefile("mar_admbnda_adm2_hcp_20230925.shp")

    # Mapping et nettoyage pour la jointure spatiale
    province_mapping = {
        'Agadir Ida Outanane': 'Agadir Ida Ou Tanane',
        'Chtouka Ait Baha': 'Chtouka- Ait Baha',
        'Inezgane Ait Melloul': 'Inezgane-Ait Melloul',
        'Taroudant': 'Taroudannt'
    }

    df_indic["join_key"] = df_indic["Province"].replace(province_mapping)

    # Rendu Plotly Mapbox

        geojson=gdf_merged.geometry,
        locations=gdf_merged.index,
        color="Valeur",
        mapbox_style="open-street-map",
        color_continuous_scale="Blues"
    )
    return fig_map

Interaction

  • Tooltips — hovering a territory shows its name and exact value, so a reader never has to infer a number from a colour scale.
  • Framing — the view is pre-centred on Souss-Massa (lat 30.2, lon −9.0) at a zoom level that fits the region on load.
  • Filtering — year, indicator and granularity (province or commune) are driven by st.session_state; each change recomputes the join and redraws the map with a colour scale rescaled to the filtered data.

Trend projection

The exploration modules describe what has happened. This module extrapolates the observed trend forward, so that a reader can see the direction and rough magnitude of change rather than only its current level.

Why linear regression

The choice is dictated by the data, not by preference. Census indicators are published roughly every ten years, and the annual series rarely exceed six points. On series that short, a flexible model fits noise and produces projections that look confident and mean nothing.

  • Sample size — a handful of temporal observations cannot support a model with many parameters
  • Interpretability — a slope coefficient can be stated plainly: this indicator changes by x per year over the observed period
  • Inertia — demographic quantities move slowly, so a linear trend is a defensible first approximation

Pipeline

  1. Preparation — series reshaped with pd.melt to isolate year as the independent variable from the target indicator.
  2. Temporal split — train and test split chronologically, with no shuffling. Shuffling a time series would train on future points and test on past ones, which inflates the score without improving the model.
  3. Fit and evaluate — the model is fitted on the earlier portion and scored on the held-out later portion using mean absolute error.
  4. Projection — future years are generated and passed through the fitted model to produce the displayed curve.
Show code

import numpy as np
import pandas as pd
from sklearn.linear_model import LinearRegression
from sklearn.metrics import mean_absolute_error


def forecast_metric(df_hist, target_col="Population", horizon=3):
    df_hist = df_hist.copy()
    df_hist["Année"] = pd.to_numeric(df_hist["Année"], errors="coerce")
    df_hist[target_col] = pd.to_numeric(df_hist[target_col], errors="coerce")

    df_hist = df_hist.dropna(subset=["Année", target_col])
    df_hist = df_hist.sort_values("Année")

    split_idx = int(len(df_hist) * 0.8) if len(df_hist) >= 6 else max(len(df_hist) - 1, 1)

    train = df_hist.iloc[:split_idx]
    test  = df_hist.iloc[split_idx:]

    X_train = train["Année"].values.reshape(-1, 1)
    y_train = train[target_col].values

    X_test  = test["Année"].values.reshape(-1, 1)
    y_test  = test[target_col].values

    model = LinearRegression()
    model.fit(X_train, y_train)

    if len(test) > 0:
        y_test_pred = model.predict(X_test)
        mae = mean_absolute_error(y_test, y_test_pred)
    else:
        mae = None
    last_year = int(df_hist["Année"].max())

    future_years = np.arange(
        last_year + 1,
        last_year + 1 + horizon
    )

    y_future = model.predict(
        future_years.reshape(-1, 1)
    )


    df_future = pd.DataFrame({

        "Année": future_years,

        f"{target_col}_pred": y_future

    })


    return model, df_future, mae

What the projections show

Each view plots observed values against fitted and projected values, so the gap between the two is visible rather than hidden behind a single extrapolated line.

Read together, the total, urban and rural trajectories show concentration rather than uniform growth: some provinces absorb increase faster than others, which translates into pressure on housing, mobility and public facilities in those territories specifically.

Limitations

These projections extrapolate an observed trend. They are not forecasts in the statistical sense, and the following constraints should be read alongside every figure produced by this module:

  • Short series. Most indicators offer between four and six temporal points. Confidence intervals on a regression fitted to so few observations are wide, and are not displayed on these charts.
  • No structural change modelled. A linear fit assumes the mechanism producing the trend continues unchanged. It cannot represent a policy shift, an economic shock, or a change in census methodology.
  • Univariate. Each indicator is projected from its own history alone. No exogenous variable — climate, public investment, migration — enters the model.
  • Held-out error only. Evaluation uses mean absolute error on the final portion of each series. With series this short, that estimate is itself unstable.

The module is intended to make the direction of change legible, not to produce figures suitable for planning decisions on their own.

Possible extensions

  • Seasonal models. If HCP publishes at monthly frequency, a model handling seasonality (such as Prophet) would apply to the CPI series, which already has monthly granularity.
  • Multivariate models. Composite indicators such as poverty depend on several measured quantities; a gradient-boosted model over multiple features would fit that structure better than a univariate line.
  • Exogenous variables. Adding geospatial or external data — climate, public investment programmes — as features, provided enough observations exist to justify the added parameters.

Question answering assistant

Charts have a limit: they answer the question they were designed for. A reader who wants a specific figure, or a comparison nobody anticipated, has to hunt for it. The assistant exists to close that gap — not as a general-purpose chatbot, but as a module restricted to the loaded dataset.

How it is constrained

Every request sends the cleaned indicator dictionary from hcpdata.py to the model as context, together with a system prompt instructing it to answer only from that context. The model is therefore working from the same numbers the charts use, in the same structure.

Grounding the model in a fixed dataset substantially reduces the risk of invented figures, because the correct values are present in the prompt and the model is instructed not to go beyond them. It does not eliminate it: a language model can still misread a nested structure or mis-attribute a value, and answers on consequential figures should be checked against the tables, which the interface displays alongside every chart for exactly this reason.

Conversation handling

  • History — exchanges are stored in st.session_state, so follow-up questions ("and how did that change since 2004?") resolve against the previous turn.
  • Formatting — the system prompt asks for Markdown, which Streamlit renders natively as tables and lists rather than a wall of text.

Automated PDF reporting

An analysis that cannot be circulated has limited use in an administrative setting. This module turns a selected dataset into a formatted PDF document, assembled without manual editing.

Report contents

  • Descriptive statistics — mean, standard deviation and quartiles computed per numeric column, with top and bottom ten rankings to expose disparity between localities.
  • Charts — Plotly and Matplotlib figures exported as images and embedded in the document flow.
  • Structure — a generated table of contents, automatic pagination, and section headings, built by extending the FPDF class with custom header, footer and TOC handling.

Export

  • Encoding — latin-1 handling so French text and locality names render correctly.
  • Naming — files are named Title_Date.pdf automatically, which keeps successive exports sortable.
  • Delivery — st.download_button streams the in-memory buffer straight to the browser, with no server-side storage.

Outcome

The platform is deployed and publicly accessible. It consolidates fifteen HCP spreadsheets across six domains into a single interface where an indicator can be filtered, mapped, compared and extrapolated without reopening a source file.

Three parts of the work were the most technically demanding, and are the ones I would defend:

  • The cleaning pipeline. The failure modes of these spreadsheets are silent rather than loud — a column read as text still sorts, a subtotal row still averages. Handling them explicitly is what makes every downstream figure reliable.
  • The spatial join. Reconciling statistical tables with boundary geometry required normalising territorial keys on both sides; without it, the maps would simply have been missing rows.
  • Constraining the assistant. Injecting the cleaned dictionary as context, rather than letting a general model answer from its own knowledge, is what keeps the answers tied to the published data.

What I would do differently

The forecasting module is the weakest part of the project, and knowingly so: the data does not support more than trend extrapolation. If I revisited it, I would display confidence intervals rather than a single line, and state the held-out error next to each projection in the interface itself — not only in the code.

Next steps

  2. Forecasting. Move to seasonal and multivariate models where series length allows, and surface uncertainty in the interface.
  3. Deployment. Containerise the application with Docker for institutional servers, and add a caching layer for larger data volumes.
