Carrefour Sales Analysis

An end-to-end business intelligence workflow on 10,000 retail transactions, built as a layered pipeline rather than a single report file.

This page documents the full chain: what the raw export looked like, which inconsistencies had to be resolved before any measure could be trusted, why the model was structured as a star schema, and what the eight dashboard views are each for.

Objective

The dataset is a retail transaction export: 10,000 orders across 19 columns, covering order lines, product categories, payment methods, customer demographics, cities, discounts, and cancellation reasons.

A spreadsheet of that size answers single questions well and comparative questions badly. Asking which categories carry the highest cancellation rate, or whether discounting actually moves revenue, means rebuilding the same pivot tables every time. The purpose of the project was to replace that with a model where those questions are already expressed as measures.

Questions the dashboard is built to answer

  • How much revenue is validated, and how much is lost to cancellations?
  • What is the effect of discounting on revenue, by category and over time?
  • Which categories, cities and payment methods perform best?
  • How do sales move month over month and year over year?
  • Which customer segments — by gender, age band, basket size — drive volume?

Pipeline

The project is deliberately split into stages rather than done inside Power BI alone. Cleaning happens in Python, where it is versioned and repeatable; modelling and measures happen in Power BI, where they belong.

  1. Raw layer — the untouched source export, kept as the reference point.
  2. Python ETL — a single script producing a clean, analysis-ready CSV.
  3. Processed layer — the cleaned dataset, with stable types and column set.
  4. Star schema — one fact table and seven dimensions built in the Power BI model.
  5. DAX measures — KPIs and time intelligence defined on top of the model.
  6. Reporting layer — eight interactive dashboard views.

Keeping cleaning outside the report matters: a transformation written in Power Query lives inside a binary file, while a Python script can be read, reviewed and re-run on a new export. Anyone can regenerate the processed dataset from the raw one with a single command.

ETL and data preparation

The ETL script (ETL/etl.py) takes the raw export and produces the processed dataset. Each transformation exists because of a specific defect in the source file.

Encoding

Retail exports arrive in whatever encoding the exporting system used. The reader attempts UTF-8, UTF-8 with BOM, CP1252 and Latin-1 in turn, and falls back to replacement characters rather than failing outright — so a single unusual byte in a city name cannot stop the pipeline. 

def read_csv_smart(path: Path) -> pd.DataFrame:
    for enc in ("utf-8", "utf-8-sig", "cp1252", "latin1"):
        try:
            return pd.read_csv(path, encoding=enc)
        except UnicodeDecodeError:
            continue
    return pd.read_csv(path, encoding="cp1252", encoding_errors="replace")

Text normalisation

Trailing whitespace in a category or city name creates duplicate members in a dimension — "Lahore" and "Lahore " become two rows in every visual. Text columns are stripped, and the literal strings "nan", "none" and "null" — which arrive as text, not as missing values — are converted to true nulls.

Dates, months and years

The month column arrives in inconsistent forms across exports. The script parses it, and if fewer than 60% of values parse successfully, it discards the column and derives the month from order_date instead. The year is derived the same way when absent. A date dimension is only as good as the key it joins on.

Discount reconciliation

The most consequential fix. In the raw file, discount_amount does not consistently agree with value × Discount_Percent: the two disagree by a factor of one hundred on part of the rows. Left alone, every discount measure would be wrong — and wrong in a way that still produces plausible-looking totals.

The script recomputes the expected amount, compares it to the stored one, and substitutes the expected value wherever the two diverge beyond a tolerance. 

da100    = df["discount_amount"] * 100.0
expected = (df["value"] * df["Discount_Percent"] / 100.0) * 100.0

use_expected = (da100 - expected).abs() > 1e-2
df["discount_amount"] = da100.where(~use_expected, expected)

Types and contract

Identifiers and counts are cast to nullable integers, monetary fields to floats, and the output is restricted to a fixed list of 18 columns. If any expected column is missing, the script raises rather than writing a partial file — so a malformed export fails loudly at the ETL stage instead of silently at the reporting stage.

Data layers

The project has no enterprise warehouse behind it, but it follows the same separation of concerns, which is what makes the pipeline auditable.

LayerContentsRule
RawOriginal export, 10,000 rows × 19 columnsNever modified
ProcessedCleaned dataset, 10,000 rows × 18 columnsRegenerated by script only
ReportingPower BI model, measures and viewsReads processed only

One column is dropped between layers (a redundant selling-price field), and no rows are lost: the row count is identical before and after, which is the first thing to check when a cleaning script silently filters data.

Star schema

The cleaned table is a flat file. Loading it directly into Power BI works, but every filter then scans the full width of the table and every relationship has to be inferred. Restructuring it as a star schema separates what is measured from what it is measured by.

Fact table

Fact_Sales — one row per order line, carrying the numeric quantities: value, quantity ordered, price, discount amount and percent.

Dimensions

  • Dim_Date — calendar for time intelligence
  • Dim_Produit — product and category
  • Dim_Client — gender, age band
  • Dim_Geography — city
  • Dim_Payment — payment method
  • Dim_Status — order status
  • Dim_Refund — cancellation and refund reason

What the structure buys

  • Simpler DAX. Time intelligence functions expect a dedicated date table; without Dim_Date, year-to-date and prior-year measures have to be written by hand.
  • Unambiguous relationships. Each filter path from a dimension to the fact table is single and directional.
  • Readable model. A reader opening the file sees the business structure, not a 19-column rectangle.

DAX measures

Measures are where business questions become reusable definitions. Writing "revenue" once, correctly, means every visual that uses it agrees.

Base measures

Total Sales    = SUM(FactSales[value])
Total Orders   = COUNT(FactSales[order_id])
Total Quantity = SUM(FactSales[qty_ordered])
Total Discount = SUM(FactSales[discount_amount])
Average Order Value = AVERAGE(FactSales[value])

Validated versus cancelled revenue

Total revenue on its own is misleading when a share of orders is later cancelled. Splitting the measure keeps the two visible side by side, and makes the cancellation rate a first-class indicator rather than something inferred.

  • CA_Validé — revenue on validated orders
  • CA_Annulé — revenue lost to cancellations
  • Taux_Annulation % — cancellation rate
  • Taux_Discount_Global — overall discount rate

Time intelligence

Built on Dim_Date, these give the dashboard its comparative dimension — a figure means little without the equivalent period beside it.

  • CA_MoM_Prev — previous month revenue
  • CA_PY — same period, previous year
  • CA_YTD — year to date
  • Croissance_CA_YoY % — year-over-year growth
Monthly Sales = CALCULATE([Total Sales], ALLEXCEPT(DimDate, DimDate[Month]))

Behavioural measures

  • Articles_par_Panier — items per basket
  • Taux_Discount_Moyen — average discount rate

Dashboard views

Eight views, each answering one family of questions. Splitting them this way keeps each page readable instead of producing a single crowded canvas.

Sales overview

Headline KPIs, revenue by category, and discount exposure at a glance.

Transaction details

Line-level drill-through with filters on order, customer and category — the view used to verify any figure seen elsewhere.

Discounts and promotions

Discount rate by category and payment method, tracked over time against revenue.

Cancellations and refunds

Cancellation volume, dominant reasons, and the revenue they represent.

Payment analysis

Comparison of payment methods by order volume, value and cancellation rate.

Geography

Commercial performance by city, to identify where volume concentrates.

Customer insights

Segmentation by gender, age band and purchase volume.

Time trends

Monthly evolution, cumulative year-to-date and growth against the prior year.

Outcome

The deliverable is a Power BI template plus the pipeline that feeds it: raw data, ETL script, processed dataset and model. Pointing the script at a new export regenerates the whole thing.

Two parts of the work were the ones that mattered:

  • The discount reconciliation. A hundred-fold discrepancy between the stored discount and the one implied by value and percentage would have corrupted every promotion measure while still producing believable totals. Finding it required checking the arithmetic rather than trusting the column.
  • Separating cleaning from reporting. Putting the transformations in a versioned script rather than in Power Query is what makes the result reproducible by someone else.

Limitations

  • Single static export. The pipeline runs on one file; there is no scheduled refresh or incremental load.
  • No data quality report. The script fixes what it finds but does not log how many rows each correction touched — which would be the natural next step.
  • Dimensions built in-model. The star schema is constructed inside the Power BI file rather than materialised as separate tables, so it is not reusable outside this report.

Next steps

  • Emit a data quality summary from the ETL — rows affected per correction, null counts per column.
  • Materialise the dimensions as CSVs or database tables, so the model is portable.
  • Add row-level security if the report were shared across regional teams.
